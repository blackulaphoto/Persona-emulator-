## Step 12: restoring psychological responsiveness — "keep the new brain, open the nerves back up"

**The problem.** After Step 11's State/Trait split, a persona could go through a full six-event life — friend rejection at 10, discovering parental conflict at 12, public humiliation at 14, an unstable first love at 16, family loss at 18, and a sexual assault by a trusted friend at 20 — and the board would still show "All is well right now" with a completely unmoved Big Five. The generated narrative for that same persona correctly described heightened threat sensitivity, avoidance, relational insecurity and guardedness. **The model understood the life. The board didn't show it.**

Step 11 had deliberately killed "one bad day moves neuroticism 20 points" and overcorrected into visibly frozen dials. Step 12 restores responsiveness *without* restoring videogame-stat psychology. The old pre-rebuild engine (`psychology_engine.analyze_experience`, still in the repo) was explicitly NOT restored: it was responsive but shallow (AI returns absolute Big Five → overwrite persona; initial symptoms came from literal keyword matching in `backstory_symptom_mapper.py`) and could not do continuity, revision, or accumulation at all.

**Five distinct causes, all found by instrumenting a real six-event run rather than reasoning about the code:**

1. **Clinical hypotheses could not accumulate across a varied life.** `evidence_accumulator` keyed hypothesis evidence off literal `exposure_type` recurrence. Emma's six events are six *different* exposure types, so nothing ever recurred and every hypothesis sat near `0.0` — while the interpretation layer had correctly recognised all six as reinforcing ONE adaptation. Fixed by adding `ADAPTATION_STRATEGY_HYPOTHESIS_SUPPORT` and a second evidence path (`_adaptation_evidence`) scaled to the adaptation's own earned strength, so a varied history converges on the same hypothesis without requiring identical event types. `developmental_pipeline` now runs evidence accumulation *after* pattern accumulation so hypotheses are never a full event behind.
2. **The same self-buffering bug fixed in `pattern_engine` existed independently in `evidence_accumulator._protective_contradiction`.** A protective factor extracted *from* an event was contradicting the hypothesis that same event opened. Fixed with the same own-event exclusion.
3. **The adaptation and hypothesis layers had no API surface at all.** They were computed and persisted since Step 11c but no route returned them, so the board could only ever render Big Five plus a threshold-gated marker list. Added `app/services/persona_board.py` + `PersonaResponse.adaptation_patterns` / `.clinical_pattern_hypotheses`, and a new `previous_evidence_strength` column (migration `010`, written defensively because this table is created by `create_all()`, not migrations) so hypotheses can show **strengthening / weakening** rather than only a number. Hypotheses deliberately surface *below* `DISPLAY_THRESHOLD` — watching the engine consider a pattern at 28% and revise it is the product's original strength; `current_trauma_markers` stays gated.
4. **Validation was all-or-nothing.** One bad key threw away an entire proposal. The model repeatedly proposed `self_reliance` as a *State* variable (confusing the two vocabularies), discarding the valid `trust`/`threat_sensitivity` movements in the same response. `_validate_proposal` now salvages per-field and logs what it dropped.
5. **Big Five was binary-gated.** Fixed with `PROVISIONAL_TRAIT_STEP` (roughly half `TRAIT_STEP`, far below `STATE_STEP`): a meaningful event nudges the slow tier immediately; crossing the establishment gate still produces the larger movement. Interventions pass `allow_provisional=False` so therapy keeps its stricter sustained-improvement gate. The tier ordering the architecture rests on is preserved and directly asserted in tests.

**Two further real bugs the instrumented run exposed, which no amount of code-reading would have caught:**

- **State polarity was inverted for the non-obvious variables.** `relational_security` *climbed* 0.62 → 0.93 across repeated betrayal ending in assault, because the bare variable name reads just as naturally as "*need for* relational security". The prompt listed names but never said which way was up. Fixed with `STATE_VARIABLE_DEFINITIONS`, injected verbatim into both the developmental and intervention prompts, each stating explicitly what HIGHER means. Guarded by tests asserting every variable has a definition and every definition says "HIGHER".
- **State saturated at the rails.** A flat step plus a hard clamp left `trust` at exactly `0.00` and `threat_sensitivity` at `1.00` by age 20 — so a *seventh* event would have produced no visible change, the same frozen-dial failure relocated into the State tier. `_stepped_value` now tapers steps in proportion to remaining headroom, approaching the bounds asymptotically. Ordinary mid-range movement is unaffected (asserted).

**Verified end-to-end with real `gpt-4o` calls, six events, capturing the board after each.** Every event moved the board. Trust fell 0.45 → 0.24, threat sensitivity rose 0.55 → 0.80, avoidance rose to 0.77; the `self_reliance` adaptation climbed emerging(–) → 20% → 40% → **established** 60% → 80%; `avoidant_personality` went 15% → 45% → 60% then **declined to 45%** on contradictory evidence while `complex_ptsd` and `ptsd` opened after the assault; a second adaptation ("Guarded Heart Sanctuary") emerged at 20; Big Five moved conservatively and cumulatively (Neuroticism 40 → 45, Agreeableness 70 → 69.4) without any single event causing an absurd jump. The age-20 event produced substantial movement across four state dimensions and two named patterns — **"All is well right now" is now structurally impossible while the state says otherwise**, because that panel reads `current_state` first and only falls back to the all-clear when the state genuinely supports it.

Full suite: 466 passed, identical `30 failed / 17 errors` pre-existing baseline (Firebase-credentials gap + dead-code tests). Step 11's original all-or-nothing trait assertions were updated to assert the corrected behavior — a deliberate product decision reversal, documented in each test, not weakened tests.

**Still open, deliberately not addressed:** the AI does not always classify a later thematically-related event under the *same* `adaptation_strategy` (Emma produced a second adaptation at 20 rather than reinforcing the first). Step 12's hypothesis-continuity work substantially reduces the impact — hypotheses now accumulate across strategies — but the underlying interpretation-consistency question is probabilistic prompt quality, not a deterministic bug.

**Two real architectural bugs were found and fixed while building the actual end-to-end pipeline test** (`tests/test_developmental_pipeline.py`) - both in `evidence_accumulator._persistence_evidence()`, both invisible until exposures, narration, and pattern formation were exercised together against a real timeline rather than each engine's own isolated unit tests:
1. A single input producing multiple exposure_types that both implicate the same pattern (e.g. "my father drank constantly and disappeared for days" → `caregiver_substance_use` + `caregiver_absence`, both pointing at `reactive_attachment_disorder`) was counted as two occurrences - one situation described two ways, read as if it had happened twice. Fixed: persistence is now keyed on distinct `(source, source_event_id)` pairs, not raw exposure-row count.
2. Persistence contributed at most one fixed-weight evidence entry (0.15) regardless of how many times something actually recurred - since exposures are the only evidence source wired into a live route so far (narration stays correctly dormant with the current case-authored UI; functional observations aren't wired into any route at all), this meant `evidence_strength` could never cross `DISPLAY_THRESHOLD` (0.4) from real recurrence alone, so `current_trauma_markers` could never populate in production no matter how much genuine history accumulated. Fixed: persistence now returns one entry per distinct occurrence beyond the first, capped at `MAX_PERSISTENCE_ENTRIES` (4).

Both are exactly the kind of bug that only an actual integration test - not per-engine unit tests, however thorough - could catch.

**Pre-existing DB-collision issue: root cause found and fixed (step 9).** The `"index ix_feedback_user_id already exists"` error blocking every DB-backed test file was originally (mis)diagnosed here as `app/main.py`'s unconditional `create_all()` colliding with test fixtures sharing a physical `test.db` file. That diagnosis was wrong. The actual cause: `app/models/feedback.py`'s `Feedback` model declared the exact same index twice - once via `user_id = Column(..., index=True)`, once via an explicit `Index('ix_feedback_user_id', 'user_id')` in `__table_args__`. This makes `Base.metadata.create_all()` fail on **any** fresh database, not just in tests - confirmed by reproducing it standalone with no test files involved. Fixed by removing the redundant explicit `Index()`. Result: DB-backed test errors dropped from 33 to 17, and none of the remainder are index/collision errors anymore. The remaining 17 are a separate, genuinely pre-existing issue - no `FIREBASE_SERVICE_ACCOUNT_JSON` configured in this local environment, so `POST /personas` returns a 401 in test fixtures that don't mock auth, cascading into `KeyError: 'id'` when the fixture tries to read the created persona's id from an auth-error response body. Not fixed here - it's an environment/credentials gap, not a code bug.

## Goal

Replace the `event -> disorder -> severity` model with `Exposure -> Interpretation -> Adaptation -> Pattern -> Reinforcement -> Current Behavior`. Preserve the product's authority, numerical state, timeline evolution, remix system, treatment simulation, and conversational simulation. Make interpretations bolder, not vaguer — but earn them with accumulated, revisable evidence instead of keyword-to-diagnosis shortcuts.

## Hard rules

1. **Operator vs. subject vs. source is a schema-level boundary, not a convention.** Every narration-derived record carries `subject_id` (the persona) and `speaker_role` (`persona_voice | case_author | third_party_report | source_material`). The engine has no schema slot for "the user" as a psychological subject — interpretations always attach to the persona. Autobiographical mode (`Persona.narrative_mode = "self_authored"`) must be set explicitly, never inferred from who is typing.
2. **Old exposure->disorder tables discover hypotheses, they never seed belief.** `symptom_assessment_engine.py`'s `EXPERIENCE_TO_DISORDER_MAPPING`/`AGE_VULNERABILITY` decide which `ClinicalPatternHypothesis` rows are worth opening. They never set `evidence_strength` at creation — that starts null and is earned from persistence, corroborating symptoms, narrative signals, and functional impact, and can be revised down by contradicting evidence.
3. **`current_trauma_markers` is a projection, not a target.** Exactly one thing writes it: a derived view over `ClinicalPatternHypothesis` rows above a display threshold. No other module writes to it directly.
4. **Protective factors are first-class, interpretation-altering state**, not a severity discount applied afterward. They're joint input to the Interpretation step alongside exposure, developmental context, and narration signals.
5. **Self-narration analysis is conditional, not a mandatory pipeline stage.** It runs *only* on text with `speaker_role == "persona_voice"` - the persona's own beliefs, memories, feelings, or speech. "Timmy was abused at 17," written by whoever is authoring the case, is a case fact and gets analyzed by the exposure extractor, never by the narration engine - how tersely or clinically a case author writes tells us nothing about Timmy, and must never be scored as if it did. This is enforced in code (`is_self_narration_eligible`), at every entry point into `self_narration_engine.py`, not left to prompt discipline.

## Evidence & Source Model

The developmental model is built from several distinct evidence channels, each with known provenance - never collapsed into "whatever the user typed":

| Channel | Informs | Status |
|---|---|---|
| **Events / exposures** — what objectively happened | `DevelopmentalExposure` (step 2). Now carries `speaker_role` for provenance (default `case_author`) - not a gate, since a fact is a fact regardless of who states it, unlike self-narration. | Built |
| **Self-report** — what the persona says, feels, remembers, believes | `NarrationRecord` / self-narration signals (step 3), gated to `persona_voice` only via `is_self_narration_eligible()` | Built |
| **Behavior** — what the persona does, observed directly | `FunctionalObservation` (`app/models/functional_observation.py`) via `app/services/functional_observation_engine.py`. Not source-gated - a behavioral claim is a fact-claim like an exposure. | Built |
| **Third-party observations** — what others report about the persona (e.g. "his mother reports he became withdrawn") | Not a separate model - a *source* (`speaker_role: third_party_report`) that applies across `DevelopmentalExposure`, `ProtectiveFactor`, and `FunctionalObservation` alike, tracked uniformly for provenance/audit. | Built (as provenance, not a distinct evidence type) |
| **Known outcomes** — relationships, work, substance use, functioning | Same `FunctionalObservation` model as Behavior (`observation_type` covers `relationship_functioning`, `occupational_functioning`, `substance_use_pattern`, etc.) - deliberately unified rather than a second parallel model, since both are "current/ongoing functioning" claims. | Built |
| **Interventions** — what was attempted and what changed | `Intervention` model exists (pre-dates this rebuild); not yet wired as evidence into `ClinicalPatternHypothesis`/`AdaptationPattern` - depends on step 7's treatment-engine rewrite to know *outcomes*, not just occurrence, so it isn't wired yet. | Not built |

The engine gets *more certain and more psychologically detailed as better evidence is added*, not *requires* first-person material to produce a real interpretation. Verified end-to-end: a case built entirely from a terse case-author fact ("Timmy was physically abused by his father at 17") plus a behavioral observation ("avoids physical contact and becomes visibly tense when his father is mentioned") - zero first-person text anywhere - correctly produces real, non-null `evidence_strength` on `ptsd`/`complex_ptsd` (from the functional-impact evidence, not from fabricated self-narrative), a genuine `hypervigilance` interpretation, and populated `current_manifestations` on both the hypothesis and the emerging pattern. This is why `pattern_engine.py`'s interpretation prompt explicitly permits "Timmy plausibly holds diminished trust in relational stability" (an inferred formulation) while forbidding an invented first-person quote when no self-report evidence backs one.

**`FunctionalObservation` evidence rules** (`app/services/evidence_accumulator.py`, `app/services/pattern_engine.py`): a `"concerning"` valence observation whose `candidate_pattern_keys` names a pattern is real supporting evidence for `ClinicalPatternHypothesis` (finally filling the `functional_impact` evidence slot left stubbed in step 4). A `"protective"` valence observation contradicts by domain overlap - same mechanism as `ProtectiveFactor`, not a separate special case. For `AdaptationPattern`, functional observations populate `current_manifestations` by domain overlap only and deliberately do **not** feed `evidence_strength` math there - that stays reserved for actual recurrence across the timeline (the Reinforcement step), keeping "is this pattern real" and "how does it show up now" as two different questions answered by two different kinds of evidence.

Interventions-as-evidence is the one real remaining gap, flagged rather than silently assumed covered.

## Implementation order

1. **Schemas** (this step) — additive only, non-breaking.
2. **Developmental Exposure Extractor** (`app/services/developmental_exposure_engine.py`, done) — replaces `backstory_symptom_mapper.py`'s role. Emits `{exposure_type, developmental_domains, raw_text, age_hint}` plus a parallel `protective_factors` list, never a disorder. AI path (GPT-4, temperature 0.2, controlled vocabulary, explicit negation/denial/hedging rules) with a keyword-plus-negation-window fallback for when the AI call fails. 14 tests in `tests/test_developmental_exposure_engine.py`, including the negation invariant ("I was not abused" / "nobody ever hit me" produce no exposure) and taxonomy-integrity checks. `build_exposure_and_protective_rows()` converts extraction output into unsaved `DevelopmentalExposure`/`ProtectiveFactor` ORM rows. **Not yet wired into `personas.py` or `experiences.py`** — those routes still call the old mapper; swapping them over is a deliberate next step, not bundled into this one.
3. **Self-Narration Engine** (`app/services/self_narration_engine.py`, done, revised) — analyzes *how* something is said, not just *what* happened: 27-signal controlled vocabulary (minimization, contradiction, normalization, idealization/devaluation, self-/other-blame, agency language, omission, caregiver framing, affect-content mismatch, etc.), plus 0-2 candidate interpretive hypotheses per input (the "protective narrative" style output), explicitly framed as hypotheses, not conclusions. AI path with a heuristic fallback (deliberately modest - only catches absolutist language, explicit self-blame phrasing, and rapid-closure minimization; produces no hypotheses, since forming an interpretive hypothesis from raw text isn't something a regex fallback should attempt). The operator/subject/source boundary is enforced in code, not just prompted: `_enforce_subject_attribution` regex-rejects any output addressing "you"/"your"/"the user" (broadened after `pattern_engine.py`'s tests caught "you believe..." slipping past an earlier, narrower phrase list), and `attributed_to_persona` is set from the caller's `speaker_role` input, never trusted from the AI's own output. **Revised: gated by `is_self_narration_eligible()` at every entry point** (`analyze_narration_ai`, `analyze_narration_async`, `analyze_narration`) - runs only when `speaker_role == "persona_voice"`. Case-author prose, third-party reports, and source material never reach the AI or heuristic path, regardless of phrasing; a terse case fact like "Timmy was abused at 17" now correctly produces zero narrative signals instead of risking signals derived from the case author's writing style. Tests confirm the AI is never even called for non-`persona_voice` text (mocked and asserted `not_called`), and that a phrase which *would* trigger the heuristic directly is correctly suppressed when routed through the gated entry points. 28 tests in `tests/test_self_narration_engine.py`. **Not yet wired into any route.**
4. **Evidence accumulator** (`app/services/evidence_accumulator.py`, done) — the single writer for pattern/symptom state. `EXPOSURE_HYPOTHESIS_PRIORS` (the direct replacement for `symptom_assessment_engine.py`'s `EXPERIENCE_TO_DISORDER_MAPPING`, re-keyed to the new exposure taxonomy) decides which `ClinicalPatternHypothesis` rows are worth *opening* - opening never sets `evidence_strength`, which starts `None`. Strength is earned only from: persistence (the same exposure_type recurring across ≥2 exposures), corroborating `persona_voice` narrative signals (third-party/case-author narration is explicitly excluded from this, per the attribution rule), and reduced by protective factors whose buffered domains overlap the pattern's implicated domains (contradicting evidence, not a silent discount). ## Step 11 (planned, not yet built): State/Trait split — subordinating Big Five to the developmental engine

**The decision.** `psychology_engine.py`'s `analyze_experience` (still called from `experiences.py::add_experience`, unchanged by the wiring above) has its own independent worldview: one GPT call per experience decides `immediate_effects` — new Big Five numbers — directly, with no relationship to `DevelopmentalExposure`/`Interpretation`/`AdaptationPattern`. That's the exact "event → disorder/number" shortcut this whole rebuild replaced everywhere else, still live at the one place a user actually watches a number move. Fix: Big Five stops being an independently-generated value and becomes a **derived output of the developmental engine**, gated by two things the codebase already has a concept of - accumulated pattern status and evidence strength - not a third parallel model.

**Two tiers, not one.**
- **State** (new) — fast-moving: trust, threat_sensitivity, mood, regulation, avoidance, relational_security. Can move meaningfully after a single event, the way `Interpretation`/`AdaptationPattern` already record a reaction per event.
- **Trait** (existing) — `Persona.current_personality` (Big Five). Slow-moving by design: from here on it may only move when a pattern has reached `AdaptationPattern.status == "established"` (already the highest evidence bar `pattern_engine.accumulate_patterns()` enforces - see step 5) or on documented sustained treatment effect (step 11e below). A single interpretation, however dramatic, must never move it - this is the literal fix for "boss yells at Michael at 24, neuroticism 57→59."

**What stays deterministic vs. what the AI reasons about.** The AI (extending `pattern_engine.interpret_experience_ai`'s existing per-event reasoning, not a new independent prompt) proposes `state_implications: {variable: {direction, magnitude}}` and `trait_implications: {trait: {direction, magnitude, evidence_strength}}` — direction and a 3-tier magnitude (mild/moderate/high), never a raw number, matching how `adaptation_strategy`/`belief_statement` are already produced today. Code then applies a small, fixed magnitude→step-size table (deliberately *not* a disorder/event coefficient table like the one this rebuild already removed from `symptom_assessment_engine.py` — see "Retire") plus the pattern-status/evidence-strength gate for Trait. The engine decides *which* variable moves and *why*; code only enforces bounds, inertia, and the gate.

**Schema additions (additive, no breaking change to existing fields):**
- `Persona.current_state` (JSON, new column) — the fast tier, parallel to and independent of `current_personality`.
- `PersonalitySnapshot.state_profile` (JSON, new column, nullable) — parallel to the existing `personality_profile`, so before/after comparisons (the thing the user explicitly does not want to lose) capture both tiers at every experience/intervention, reusing the snapshot infrastructure that already exists rather than a new table.
- `Interpretation.state_implications` / `Interpretation.trait_implications` (JSON, new columns, nullable) — `Interpretation` already is the per-event row (`belief_statement`, `adaptation_strategy`, `reasoning`); this is where the AI's proposed implications naturally attach, not a new record type.
- New Pydantic schema `DevelopmentalAnalysisResult` (`app/schemas/developmental_analysis.py`) — the canonical internal shape: `verdict, developmental_impact, exposures, interpretations, adaptations, patterns_reinforced, protective_factors, state_changes, trait_changes, clinical_pattern_changes, evidence_strength, reasoning`. Becomes what `process_developmental_text()` returns (extending its current `{exposures, protective_factors, trauma_markers, interpretation}` dict, not replacing the function's role).

**Immediate vs. developmental, mapped onto what already exists** — the user's four-tier example (immediate state response → emerging adaptation → long-term pattern → trait implication) turns out to already be three-quarters built:
1. Immediate state response (new) → `state_implications` / `Persona.current_state`.
2. Emerging adaptation → already `Interpretation.adaptation_strategy` (step 5, built).
3. Long-term pattern, if reinforced → already `AdaptationPattern` (step 5, built).
4. Trait implication (new, gated) → `trait_implications`, applied only at `status == "established"`.

**Legacy Experience Adapter.** New `app/services/legacy_experience_adapter.py::to_legacy_experience_fields(result: DevelopmentalAnalysisResult) -> dict` produces exactly the response shape `experiences.py` returns today (`immediate_effects, long_term_patterns, symptoms_developed, symptom_severity, coping_mechanisms, worldview_shifts, cross_experience_triggers, recommended_therapies`), so the frontend's `ExperienceResponse` contract does not change. This is the piece that lets `experiences.py::add_experience` stop calling `psychology_engine.analyze_experience` (retiring its independent GPT call, not just leaving it running alongside the new pipeline as it does today) without touching the frontend. `immediate_effects` specifically stops meaning "new Big Five values" and starts meaning "state_changes translated into the old field shape for display only" - the field name is kept for compatibility, its meaning is not.

**Treatment (extends step 7, doesn't replace it).** `intervention_engine.analyze_intervention` gains the same `state_implications`/`trait_implications` shape. A single intervention primarily produces state movement (regulation, avoidance, coping - matching `PATTERN_KEY_THERAPY_ALIASES`'s existing mechanism-vs-target framing). Trait movement from treatment requires the same gate as trait movement from experience: documented improvement sustained across multiple interventions targeting the same pattern, not one good session.

**What this deliberately does NOT introduce**, matching the "no 75-coefficient formula" instruction directly: no event-type × trait-delta lookup table, no numeric severity multiplier keyed on age or event category. The only two hardcoded things are a 3-step magnitude scale (shared by State and Trait, different constants) and the existing evidence/status gate. Every "which trait, which direction, how strongly evidenced" judgment stays with the AI reasoning step, exactly where step 5 already put adaptation-strategy judgments.
